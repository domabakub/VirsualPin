# Virtual Phin — UX/UI audit

วันที่ 31 สิงหาคม 2026 · ตรวจ local working tree ใน S:/Hackaton

**ผลประเมิน: ยังไม่พร้อมอ้างว่าผ่าน WCAG 2.2 AA หรือพร้อมใช้เป็นแพลตฟอร์มการเรียนจริง** มีปัญหาที่ตรวจพบทั้งความถูกต้องของเนื้อหา การใช้งานจอเล็ก และ accessibility ควรแก้กลุ่ม P1 ก่อนเพิ่มลูกเล่นภาพ

งานนี้เป็น audit ไม่ได้แก้ source code หรือเผยแพร่เว็บ และไม่ได้เปลี่ยนงานที่ยังไม่ commit ของผู้ใช้

## ขอบเขตและวิธีตรวจ

- ทดลองหน้า `/`, `/songs`, `/songs?category=learn`, `/play/lao-duang-duen`, `/play/free-play`, `/settings` ผ่านเบราว์เซอร์ พร้อมอ่าน component และ state ที่เกี่ยวข้อง
- ตรวจภาพจริงและ DOM ของหน้าฝึกที่ viewport 1280×720, 768×1024, 390×844 และ 320×568; ตรวจหน้าแรกและตั้งค่าบนมือถือด้วย ไม่ได้ทดสอบทุกหน้าที่ทุกขนาด
- ทดลองเลือกเพลง เปลี่ยนเมนู ค้นหาไม่พบ เริ่มฝึก ดีดโน้ตแรก โหลดใหม่ เล่นอิสระ และใช้ Tab/Shift+Tab ที่ช่องค้นหา
- ตรวจความต่างสีจากค่า CSS ด้วยสูตร relative luminance ของ WCAG ไม่ใช้สีจากขอบตัวอักษรในภาพ
- ใช้ WCAG 2.2 AA เป็นเป้าหมายด้าน accessibility; ข้อเสนอด้านรูปแบบภาพและ usability เป็นดุลยพินิจการออกแบบ ไม่ใช่ข้อบังคับ WCAG

**ข้อจำกัด:** ใช้ development server ใน Chromium ของ Codex ไม่ใช่เครื่องจริงทุกแพลตฟอร์ม ไม่เปิดกล้องหรืออนุญาตสิทธิ์ใหม่ จึงตรวจ camera loading/error จากโค้ดเท่านั้น ไม่ได้ทดสอบ tracking จริง เสียงบน Safari/iPad, screen reader จริง, 200% zoom ทุกหน้า, performance production หรือจบเพลงทั้งเพลง ผลนี้ไม่ใช่ใบรับรอง accessibility และไม่ให้คะแนน Lighthouse ที่ไม่ได้วัด

## สิ่งที่ควรรักษาไว้

- หน้าแรกมีคำสั่งหลัก “เลือกเพลงเพื่อเริ่ม” และทางเลือกเล่นอิสระชัดเจน
- ภาพพิณช่วยสื่อประเภทผลิตภัณฑ์ มีเอกลักษณ์มากกว่าภาพตกแต่งทั่วไป
- เล่นผ่านปุ่มได้โดยไม่จำเป็นต้องเปิดกล้อง เหมาะเป็นทางเลือกสำรอง
- มีชื่อภาษาไทยให้ปุ่มเฟรตและปุ่มดีด ตั้ง `lang="th"` และไม่ได้ปิดการซูมด้วย viewport
- มีการตอบสนองถูก/ผิด การแสดงคะแนน และข้อความ privacy เรื่องประมวลผลบนเครื่อง
- animation สองชุดใน global CSS เคารพ `prefers-reduced-motion`

### A01 — โน้ตบนหน้าจอไม่ตรงกับเสียงที่กำหนด

**หลักฐาน:** เพลงลาวดวงเดือนแสดง D ที่สาย 1 เฟรต 0 แต่ปุ่มดีดระบุ E4 และค่า base frequency ของสายเดียวกันคือ 329.63 Hz โค้ดตรวจถูก/ผิดจากสายและเฟรต ไม่ตรวจ label ทดลองกดแล้วได้ 100 คะแนนและเลื่อนไปโน้ตที่สอง แม้ข้อมูล pitch กับ label ขัดกัน นอกจากนี้ `transpose()` เปลี่ยนสาย/เฟรตแต่ไม่คำนวณ label ใหม่

อ้างอิง [songs.ts](S:/Hackaton/src/data/songs.ts:24), [usePhinAudio.ts](S:/Hackaton/src/hooks/usePhinAudio.ts:9), [VirtualPhinStudio.tsx](S:/Hackaton/src/components/play/VirtualPhinStudio.tsx:54)

**ผลกระทบ:** ผู้เรียนเห็นชื่อโน้ตหนึ่งแต่ได้ยินอีกชื่อหนึ่ง การให้คะแนนยืนยันความเข้าใจผิดนี้ ข้อสรุปเรื่อง pitch มาจากโค้ด ไม่ใช่การวัดสัญญาณเสียงจากลำโพง

**แก้:** กำหนด tuning และ note mapping เป็นแหล่งข้อมูลร่วมของเสียง label และ scoring ตรวจเพลงตัวอย่างกับผู้รู้ดนตรี และระบุ “แบบฝึกตัวอย่าง” หากยังไม่ใช่ทำนองที่ตรวจสอบแล้ว

**ตรวจรับ:** ทุกคู่สาย/เฟรตในเพลงต้องให้ชื่อโน้ตตรงกับ pitch ทั้ง Web Audio และ fallback; เปลี่ยน tuning หรือ transpose แล้ว label อัปเดตตาม

### A02 — หน้าฝึกไม่เหมาะกับ viewport แคบ

**หลักฐาน:** ที่ 320×568 พื้นที่ document มี client width 305px เนื่องจาก scrollbar แต่ scroll width เป็น 354px; aside กว้าง 338px และยื่นถึง x=354 ปุ่มด้านขวาและตัวพิณถูกตัด ที่ 390×844 ปุ่มเริ่มฝึกอยู่ประมาณ y=1014 และที่ 768×1024 อยู่ประมาณ y=1049 ก่อนเริ่มเพลง ต้องเลื่อนหา ส่วนโน้ตและปุ่มควบคุมอยู่คนละช่วงกับพื้นที่พิณ

อ้างอิง [VirtualPhinStudio.tsx](S:/Hackaton/src/components/play/VirtualPhinStudio.tsx:114), [VirtualPhinCamera.tsx](S:/Hackaton/src/components/play/VirtualPhinCamera.tsx:326)

**แก้:** ให้ grid items ย่อได้ด้วย `min-w-0` ตรวจ min-content ของแถวโน้ต 6 ตัว จัดโน้ตปัจจุบันและปุ่มเริ่ม/พักให้อยู่ใกล้พิณ ลดความสูงพื้นที่ว่างบนมือถือ และพับคำแนะนำรายละเอียด แสดงโน้ตถัดไปเท่าที่พื้นที่พอ ไม่ซ่อน horizontal overflow ที่ root เพื่อกลบปัญหา

**ตรวจรับ:** controls และข้อความทั่วไปไม่ล้นที่ความกว้าง 320 CSS px; ผู้ใช้กดเริ่ม อ่านโน้ตปัจจุบัน และดีดได้โดยไม่ต้องเลื่อนสลับไปมาระหว่างทุกโน้ต; ปุ่มขวาไม่ทับพื้นที่เฟรตสุดท้าย

เกณฑ์ reflow ยอมให้บางเนื้อหาที่ต้องใช้สองมิติมีข้อยกเว้น แต่ไม่ควรให้แบบฟอร์ม ปุ่ม และแผงคะแนนทั่วไปล้นตามไปด้วย [W3C: Reflow](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html)

![หน้าฝึกถูกตัดด้านขวาที่ viewport 320×568](S:/Hackaton/docs/ui-audit-2026-08-31/practice-320.png)

### A03 — ความคืบหน้าที่แสดงไม่ใช่ผลการฝึกจริง

**หลักฐาน:** หน้าแรกแสดง 7 วันต่อเนื่องและ 72% แบบ hardcoded คลังเพลงเริ่มที่ 42%, 18% ฯลฯ จาก fixture ทดลองฝึกได้ 1/12, 100 คะแนน แล้ว reload กลับเป็น 0/12 และ 0 คะแนน ไม่มีข้อความบอกว่าผลยังไม่บันทึก

อ้างอิง [HomeDashboard.tsx](S:/Hackaton/src/components/home/HomeDashboard.tsx:26), [songs.ts](S:/Hackaton/src/data/songs.ts:55), [VirtualPhinStudio.tsx](S:/Hackaton/src/components/play/VirtualPhinStudio.tsx:16)

**แก้:** ช่วงต้นแบบติดป้าย “ข้อมูลตัวอย่าง” หรือซ่อนตัวเลข เมื่อรองรับการบันทึก ให้ session, library และ dashboard ใช้ข้อมูลชุดเดียวกัน มีสถานะยังไม่เริ่ม/กำลังฝึก/สำเร็จ และแยก “ฝึกต่อ” ออกจาก “เริ่มใหม่”

**ตรวจรับ:** ผู้ใช้ใหม่เห็นข้อมูลเริ่มต้นที่ถูกต้อง; กลับหน้าเดิมแล้วข้อมูลสอดคล้องกับนโยบายบันทึก; ถ้าไม่บันทึกต้องบอกก่อนเริ่มและไม่เรียกค่าตัวอย่างว่าเป็นความคืบหน้าของผู้ใช้

### A04 — เมนูบทเรียนและคลังเพลงแยกกันไม่จริง

**หลักฐาน:** logic active ตัด query string ออก ทำให้ทั้งสองรายการเป็นสีน้ำเงินพร้อมกัน ไม่มี `aria-current` เปิด `/songs?category=learn` โดย reload ได้หนึ่งเพลง จากนั้นกด “คลังเพลง” URL เปลี่ยนเป็น `/songs` แต่ยังกรองเพลงพื้นฐานหนึ่งเพลงอยู่ เพราะ `learningMode` ใช้ตั้ง state ครั้งแรกเท่านั้น ชื่อหน้าในโหมดบทเรียนยังเป็น “เลือกเพลงที่อยากฝึก” ไม่มีโครงสร้างบทเรียน

อ้างอิง [BottomNav.tsx](S:/Hackaton/src/components/navigation/BottomNav.tsx:20), [SongLibrary.tsx](S:/Hackaton/src/components/songs/SongLibrary.tsx:52)

**แก้:** หากยังไม่มีบทเรียนจริง ให้รวมเป็นคลังเพลงพร้อมหมวด “แบบฝึกพื้นฐาน” หากคงเมนูแยก ให้ route และเนื้อหามีหน้าที่ชัดเจน sync filters กับ URL และกำหนด current item เพียงหนึ่งรายการ

**ตรวจรับ:** navigation, direct URL, reload และ back/forward ให้เนื้อหาและเมนูตรงกัน; active เพียงรายการเดียวและใช้ `aria-current="page"`

### A05 — ช่องค้นหาไม่รองรับ focus ที่มองเห็นได้

**หลักฐาน:** ทดลอง Tab/Shift+Tab แล้ว input เป็น `focused: true`, `:focus-visible: true` แต่ computed outline เป็น `none` และไม่มี focus shadow แทน ภายนอกมีเพียงเงาคงที่ของกล่อง `label` ครอบ input แต่ไม่มีข้อความ label; DOM snapshot แสดง textbox ที่ไม่มีชื่อแยกจาก placeholder

อ้างอิง [SongLibrary.tsx](S:/Hackaton/src/components/songs/SongLibrary.tsx:64), [globals.css](S:/Hackaton/src/app/globals.css:35)

**แก้:** เพิ่ม label “ค้นหาเพลง” ที่สัมพันธ์กับ input และ `focus-within` ring ที่เห็นชัด อย่าใช้ placeholder แทน label ตรวจ links, buttons และ input ร่วมกัน

**ตรวจรับ:** ใช้คีย์บอร์ดแล้วรู้ทันทีว่ากำลังอยู่ช่องใด; accessible name คงอยู่เมื่อพิมพ์ข้อความ และ focus ไม่ถูกแถบเมนูบัง [W3C: Focus Visible](https://www.w3.org/WAI/WCAG22/Understanding/focus-visible.html), [W3C: Forms](https://www.w3.org/WAI/tutorials/forms/)

### A06 — ตัวอักษรเล็กและจางในหน้าฝึก

| เนื้อหา | สีตัวอักษร / พื้นหลัง | ขนาดในโค้ด | Contrast ที่คำนวณ |
|---|---|---|---|
| ความแม่นยำ / คะแนน | #99856d / #f5efe5 | 9px | 3.10:1 |
| โน้ตปัจจุบัน | #94734c / #f2eadc | 10px | 3.65:1 |
| จำนวนโน้ตที่เล่น | #8b7962 / #f2eadc | 10px | 3.51:1 |
| สาย/เฟรตในโน้ตถัดไป | #9a866d / #fbf7ef | 8px | 3.27:1 |

ข้อมูลเหล่านี้เป็นข้อความใช้งาน ไม่ใช่ของตกแต่ง และต่ำกว่า 4.5:1 สำหรับข้อความทั่วไป [W3C: Contrast Minimum](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html)

อ้างอิง [VirtualPhinStudio.tsx](S:/Hackaton/src/components/play/VirtualPhinStudio.tsx:125)

**แก้:** ใช้ token สีข้อความรองที่เข้มขึ้น ลดจำนวนขนาดตัวอักษร เลิกใช้ 8–10px กับข้อมูลที่ต้องอ่านขณะเล่น ขนาด body 16px และ supporting text 14px เป็นเป้าหมายการออกแบบที่แนะนำ ไม่ใช่ขั้นต่ำที่ WCAG กำหนด

**ตรวจรับ:** ข้อความทั่วไปทุก state ≥4.5:1 และข้อความใหญ่ตามนิยาม WCAG ≥3:1; ตรวจ theme สีอ่อนและ overlays บนกล้องแยกกัน

### A07 — ผู้ใช้เทคโนโลยีช่วยเหลือไม่ทราบสถานะที่เปลี่ยน

**หลักฐาน:** ปุ่มเฟรตมีชื่อ แต่ไม่เปิดเผย selected/pressed state ตัวกรองใช้สีอย่างเดียวบอกการเลือก feedback “ถูกต้อง” กับคะแนนเปลี่ยนเป็น div/p ปกติ ไม่มี live region ของแอปในหน้าฝึก แถบความคืบหน้าเป็น div ตกแต่ง

อ้างอิง [VirtualPhinInstrument.tsx](S:/Hackaton/src/components/play/VirtualPhinInstrument.tsx:44), [SongLibrary.tsx](S:/Hackaton/src/components/songs/SongLibrary.tsx:68), [VirtualPhinStudio.tsx](S:/Hackaton/src/components/play/VirtualPhinStudio.tsx:152)

**แก้:** ใช้ semantics ที่ตรงกับพฤติกรรม เช่น `aria-pressed` สำหรับตัวกรองแบบปุ่ม หรือ radio group สำหรับเลือกเฟรตต่อสาย มีข้อความสาย/เฟรตที่เลือก และ status region สำหรับผลที่สำคัญ อย่าประกาศค่า tracking ทุกเฟรมหรือทุกตัวเลขจนรบกวน

**ตรวจรับ:** ใช้ screen reader จริงแล้วทราบค่าที่เลือก ผลถูก/ผิด และผลจบการฝึกโดยไม่ต้องเดาจากสี อ้างอิง WCAG 4.1.2 และ 4.1.3 [WCAG 2.2](https://www.w3.org/TR/WCAG22/)

**หลักฐาน:** ปุ่มโปรไฟล์บนหน้าแรกไม่มี handler/link หน้าตั้งค่ามี “กล้องหน้า” และ “ปานกลาง” เป็น span ไม่ใช่ controls; DOM ของหน้าไม่มีช่องให้เปลี่ยนค่า

อ้างอิง [HomeDashboard.tsx](S:/Hackaton/src/components/home/HomeDashboard.tsx:27), [Settings page](S:/Hackaton/src/app/settings/page.tsx:8)

**แก้:** ต่อฟังก์ชันให้ใช้งานได้และบันทึกจริง หรือเอาลักษณะปุ่มออกพร้อมบอก “ใช้ค่าเริ่มต้นในรุ่นทดลอง” ไม่ปล่อยให้ผู้ใช้ลองกดโดยไม่มีคำตอบ

**ตรวจรับ:** ทุก control มีผลที่สังเกตได้; เปลี่ยนค่าแล้วส่งผลถึงหน้าฝึกและคงอยู่ตามนโยบายบันทึก

### A09 — ขั้นตอนเริ่มต้นยาว และไม่บอกสถานะรอของกล้อง

**หลักฐานจากโค้ด:** hook มี phase `requesting` และ tracker มี `loading` แต่ VirtualPhinCamera แสดงปุ่มตาม `isLive` อย่างเดียว ไม่ disable ระหว่างขอสิทธิ์ และไม่แสดงขั้นตอนโหลด tracker ส่วนคู่มือมือซ้าย/ขวาเจ็ดข้ออยู่ท้ายแผง ยังไม่มีแบบฝึกท่าทางทีละขั้น ข้อความหลายจุดแนะนำมือแม้กำลังใช้ปุ่มหน้าจอ

อ้างอิง [VirtualPhinCamera.tsx](S:/Hackaton/src/components/play/VirtualPhinCamera.tsx:333), [VirtualPhinStudio.tsx](S:/Hackaton/src/components/play/VirtualPhinStudio.tsx:166)

**แก้:** ให้เลือก “แตะหน้าจอ” หรือ “ใช้กล้อง” แล้วแสดงคำแนะนำตามโหมด จัด 3 ขั้น: ทดสอบเสียง → ลองเลือกเฟรต/ดีดหนึ่งโน้ต → เริ่มเพลง สำหรับกล้องบอกกำลังขอสิทธิ์/กำลังโหลด/พร้อม/ไม่พบมือ/ผิดพลาด และมีวิธีเปลี่ยนไปใช้ปุ่มเสมอ

**ตรวจรับ:** ผู้เริ่มต้นทำเสียงแรกได้จากคำแนะนำบนหน้าโดยไม่ต้องอ่านคู่มือยาว; เมื่อรอหรือปฏิเสธกล้อง ผู้ใช้ทราบสาเหตุและทางไปต่อ ต้องทดสอบบนกล้องจริงภายหลัง

### A10 — โหมดอิสระและวงจรการฝึกยังให้ข้อมูลไม่ตรงบริบท

**หลักฐาน:** โหมดอิสระแสดงความแม่นยำ 0% และคะแนน 0 แม้กดเล่นแล้ว เพราะไม่ให้คะแนน แต่ยังใช้ข้อความ “หรือกดเริ่มฝึก” โดยไม่มีปุ่มเริ่มฝึก ส่วนโหมดเพลงมีเริ่มใหม่ที่รีเซ็ตทันที ไม่มีพัก/ฝึกต่อ ในโค้ด completion มีคำว่า “จบ” และ feedback แต่ไม่มี flow สรุปผลกับขั้นตอนถัดไปที่แยกชัด

อ้างอิง [VirtualPhinStudio.tsx](S:/Hackaton/src/components/play/VirtualPhinStudio.tsx:21), [VirtualPhinStudio.tsx](S:/Hackaton/src/components/play/VirtualPhinStudio.tsx:90)

**แก้:** โหมดอิสระแสดงโน้ต/สาย/เฟรตที่กำลังเล่นแทนคะแนนที่ใช้ไม่ได้ โหมดเพลงมีพัก/ต่อ เริ่มใหม่ที่ป้องกันการล้างผลโดยพลาด และผลสรุปเมื่อเล่นจบ ระบุว่า “ความแม่นยำของสาย/เฟรต” เพราะ scoring ปัจจุบันยังไม่วัดจังหวะตาม beat

**ตรวจรับ:** แต่ละโหมดมีข้อความและ controls ตรงกับสิ่งที่ทำได้; เล่นจบแล้วมีทางเลือกฝึกซ้ำหรือเลือกเพลงต่อ; ไม่สื่อว่าได้ประเมินจังหวะหรือท่าทางมากกว่าที่ระบบทำจริง

### A11 — ภาษาภาพและ affordance ยังไม่เป็นระบบเดียวกัน

**หลักฐาน:** Home/Library/Settings ใช้ฟ้า-ขาว แต่ Studio ใช้น้ำตาล-ครีมและพื้นพิณดำ ขณะที่ global token ยังเป็น jade/dark ทำให้ focus สีเขียวสว่างหลุดจากทั้งสองธีม คลังเพลงมี card hover ทั้งกล่องแต่เข้าเพลงได้เฉพาะปุ่มวงกลม 40px ตัวพิณมีปุ่มดีด 32px และเฟรตกว้างประมาณ 31px ที่จอ 390px เมนูล่างของ Settings อยู่ราวกลางล่างของหน้า ไม่ชิดก้น viewport เพราะใช้ sticky ใน normal flow

อ้างอิง [globals.css](S:/Hackaton/src/app/globals.css:3), [SongLibrary.tsx](S:/Hackaton/src/components/songs/SongLibrary.tsx:33), [BottomNav.tsx](S:/Hackaton/src/components/navigation/BottomNav.tsx:17)

**แก้:** ใช้ชุด token ร่วมสำหรับสีข้อความ primary action border focus radius และ spacing เก็บสีน้ำตาลไม้กับภาพพิณเป็นเอกลักษณ์ได้ แยก Studio เป็นโหมดเข้มได้หากทำอย่างตั้งใจ กำหนด click target ของ card ให้ตรงกับภาพและไม่ซ้อนลิงก์ จัดตำแหน่ง nav ให้คงที่พร้อมเผื่อ safe area และไม่บัง focus

**ตรวจรับ:** ปุ่มชนิดเดียวกันหน้าที่เดียวกันมี style และ state เดียวกัน เป้าหมายปุ่มสัมผัสทั่วไป 44×44px เป็นข้อเสนอของงานนี้; WCAG 2.5.8 AA ใช้ 24×24 CSS px หรือเข้าเงื่อนไขข้อยกเว้น จึงไม่เหมารวมว่าปุ่ม 32px หรือ 40px ไม่ผ่าน AA [W3C: Target Size Minimum](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html)

## แนวทาง UX/UI ที่เสนอสำหรับรอบปรับ

| ส่วน | รูปแบบที่เสนอ | เหตุผล |
|---|---|---|
| หน้าแรกผู้ใช้ใหม่ | อธิบายเล่นโดยไม่ใช้กล้องได้ + “ลองเล่นโน้ตแรก” | ลดขั้นตอนเริ่มต้น |
| หน้าแรกผู้ใช้เดิม | “ฝึกต่อ” พร้อมเพลง/ความคืบหน้าจริง | กลับมาทำงานเดิมได้เร็ว |
| คลังเพลง | search มี label, filter มี selected state, จำนวนผลลัพธ์, clear filters เมื่อไม่พบ | หาเพลงและแก้การค้นหาที่ติดขัดได้ |
| หน้าฝึก | โน้ตปัจจุบัน → พิณ → ปุ่มเริ่ม/พักอยู่กลุ่มเดียวกัน | ลดการสลับสายตาและเลื่อนจอ |
| คำแนะนำ | คำแนะนำสั้นตามโหมด + เปิดรายละเอียดเมื่อจำเป็น | ไม่ให้คู่มือแย่งพื้นที่เล่น |
| จบการฝึก | ผลสรุปที่วัดจริง + ฝึกซ้ำ/เพลงต่อไป | จบงานและต่อยอดได้ |

ข้อเสนอ design system: body 16px, supporting 14px, label 12px เมื่อยังอ่านสบาย, line-height ภาษาไทยประมาณ 1.5–1.7; spacing 4/8/12/16/24/32; radius ปุ่ม 12–16 และ cards 20–24px; primary action หนึ่งชนิดต่อหน้าจอ; สี success/warning/error พร้อมข้อความหรือไอคอนเสมอ ตัวเลขเหล่านี้เป็นแนวทางเริ่มต้นที่ต้องทดสอบ ไม่ใช่มาตรฐานรับรองความสวยงาม

## แผนแก้ที่ตรวจรับได้

1. **ความถูกต้องและงานหลัก:** A01–A04 ปรับ pitch mapping, reflow, progress และ navigation ก่อน
2. **พื้นฐาน accessibility:** A05–A07 ทำ label/focus/contrast/state ให้ครบ ไม่รอ redesign เสร็จ
3. **Flow และ component system:** A08–A11 ทำ controls จริง onboarding results และ tokens ร่วม
4. **ตรวจซ้ำก่อน release:** คีย์บอร์ดทั้ง flow, screen reader จริง, 320/390/768/1280px, zoom 200%, portrait/landscape, กล้องอนุญาต/ปฏิเสธ/ไม่พบอุปกรณ์ และ audio บน Safari/iPad จริง ใช้ production build วัด performance แยกจาก audit นี้

เกณฑ์ usability ที่เสนอ: ให้ผู้เริ่มต้นลองเลือกเพลง ทำเสียงแรก พัก และกลับมาฝึกต่อโดยไม่มีคนบอกวิธี สังเกตจุดติดขัดและเวลาในการทำงานก่อน/หลังแก้ ไม่อ้างผล usability test จนกว่าจะได้ทดสอบกับผู้ใช้จริง
